## Contexto

TS-020 (`system/BACKLOG.md`, auditoría UX 2026-07-24): `src/server/api/routers/insumo.ts` solo expone `list` y `updateStockMinimo` — no hay forma de crear un insumo nuevo ni por UI ni por API. Si Dani necesita empezar a comprar un ingrediente nuevo (ej. "Carne picada"), hoy queda bloqueada sin que un dev intervenga a mano en la base.

**Alcance acotado a propósito**: el hallazgo original también mencionaba "agregar producto nuevo" (ej. una variedad de empanada nueva) en `/produccion`. Se descarta acá: un producto nuevo sin receta configurada (`RecetaItem`) no sirve para nada — `lote.create` rechaza cualquier producto sin receta (`src/server/api/routers/lote.ts:49-54`) y el módulo de Recetas todavía no existe (TS-004, deliberadamente pausado hasta tener feedback real de Dani). Agregar un producto nuevo sin forma de configurarle receta sería peor UX que no tener el botón. Cuando se construya Recetas, ahí sí tiene sentido resolver "agregar producto" como parte de ese mismo trabajo.

## Pasos sugeridos

1. **Router**: en `src/server/api/routers/insumo.ts`, agregar mutation `create`:
   ```ts
   create: protectedProcedure
     .input(z.object({
       nombre: z.string().min(1),
       unidad: z.enum(["kg", "unidad"]),
       stockActual: z.number().min(0).default(0),
     }))
     .mutation(async ({ ctx, input }) => {
       const existente = await ctx.db.insumo.findFirst({ where: { nombre: input.nombre } });
       if (existente) {
         throw new TRPCError({ code: "BAD_REQUEST", message: "Ya existe un insumo con ese nombre." });
       }
       return ctx.db.insumo.create({ data: input });
     }),
   ```
   (ajustar tipos/estilo al resto del router — es una guía, no copiar literal si no calza con el resto del archivo).

2. **UI en `/insumos`**: agregar una sección/card "Nuevo insumo" arriba o abajo de la lista existente (mismo patrón visual `bg-white rounded-xl border border-gray-200 p-4` que usan los formularios de las otras páginas), con campos nombre (text), unidad (select con "kg"/"unidad"), stock inicial (number, opcional, default 0 — aplicar F-0033 si ya está mergeado, o al menos no repetir el bug de contraste: texto del input con color explícito). Invalidar `insumo.list` en `onSuccess` (y `compra.insumo` si el selector de `/compras` usa un query separado — revisar `src/app/compras/page.tsx` para confirmar que ambos comparten el mismo `trpc.insumo.list.useQuery()` y no hace falta invalidar nada más).

3. Reusar en `/compras` el mismo `insumo.list` ya invalidado — no debería hacer falta tocar `compras/page.tsx` más que confirmar que el nuevo insumo aparece en el `<select>` sin recargar.

## Fuera de alcance

- No agregar "agregar producto nuevo" — ver nota en Contexto, queda para cuando se construya el módulo de Recetas (TS-004).
- No agregar edición de insumos existentes más allá de lo que ya existe (`updateStockMinimo`) — solo alta de insumos nuevos.
- No agregar borrado de insumos — un insumo con compras/recetas asociadas no debería poder borrarse sin pensar en las FK, y no es lo que pidió Dani. Fuera de alcance.
- No agregar categorías ni unidades más allá de "kg"/"unidad" (las dos que ya usa el sistema hoy, ver `schema.prisma` comentario `unidad String // "kg" | "unidad"`).

## Restricciones clave

- Nombre de insumo único (case-sensitive alcanza, no hace falta normalizar mayúsculas/acentos para este tamaño de app).
- No agregar dependencias nuevas.
- Mobile-first: el formulario nuevo tiene que verse bien en viewport angosto (~375px), mismo estándar que el resto de la app.
