## Contexto

**Verificado contra el código y la DB real antes de escribir este spec** (no es un supuesto):

- `scripts/cafci_sync.py` y `scripts/cafci_inspect.py` (portfolio-tracker) ya mapean
  `C["patrimonio_act"] = 14` ("Patrimonio — Actual") en cada descarga de `pb_get`. Hoy ese valor
  SOLO se usa dentro de `es_inactivo(row)` para descartar fondos sin actividad — nunca se persiste
  en ningún lado. No hace falta pegarle a `estadisticas.cafci.org.ar` (que sí requeriría scraping
  página por página, ver AR-031): el dato ya viene en el mismo archivo bulk que hoy alimenta el VCP
  diario.
- Confirmado por SQL contra el proyecto Supabase `argoscapital` (`wwzocpcolgdzkvcigchj`):
  `fci_master` NO tiene ninguna columna de patrimonio/AUM hoy (20 columnas actuales, ninguna
  matchea). Las vistas `fci_explorador` y `fci_explorador_grupos` (`pg_get_viewdef` inspeccionado)
  tampoco lo seleccionan — habría que agregarlo a ambas.
- El cron que corre `cafci_sync.py --daily` es `.github/workflows/cafci_daily.yml`: GitHub Actions,
  lunes a viernes 01:00 UTC (22:00 ART), más `workflow_dispatch` manual. **Este feature no dispara
  el workflow** — el cron sigue su calendario normal; `patrimonio` queda en `null` para todos los
  fondos hasta la primera corrida del cron después del deploy (o un `workflow_dispatch` manual que
  Augusto decida disparar).
- El script YA soporta `--dry-run` (no escribe en Supabase) — usarlo para validar el cambio de
  Python sin tocar prod.
- `mercadoService.getFondosPage`/`getFondosStats` seleccionan `'*'` de las vistas — una vez que la
  vista expone `patrimonio`, llega solo al front sin tocar esas funciones.
- `fci_master` se actualiza hoy con un patrón de `update()` individual por fondo dentro de
  `enrich()` (campos que cambian poco: gerente, depositaria, moneda, clasificación). `patrimonio`
  cambia todos los días y hay ~3.974 fondos activos con `cafci_id` — actualizarlo con ~3.974
  llamados individuales por corrida sería mucho más lento que el patrón de upsert por lotes que
  `daily()` ya usa para `fci_prices` (`BATCH_SIZE = 500`, `on_conflict="fci_id,fecha"`). Preferir un
  upsert por lotes similar (`on_conflict="id"`) sobre `fci_master` con solo `{id, patrimonio}` por
  fila — como todos esos `id` ya existen (vienen del mismo `idx` que arma `daily()` hoy), el upsert
  solo actualiza, nunca inserta una fila nueva incompleta.

**Nota importante para quien revise este feature:** la parte en Python (`cafci_sync.py`) no la
cubre el verifier del loop (`tsc`/`vitest` son JS/TS). El acceptance de arriba solo puede confirmar
automáticamente la migración, las vistas y el lado del Explorador — el cambio en `cafci_sync.py`
necesita una corrida real con `--dry-run` (o revisión manual del diff) para confirmar que upsertea
lo que dice upsertear.

## Pasos sugeridos (el planner puede refinar)

1. Migración aditiva en Supabase: columna `patrimonio numeric null` en `fci_master`. Seguir el
   patrón de migraciones ya versionadas en `supabase/migrations/` del repo (aditiva, sin tocar
   columnas existentes, sin backfill obligatorio — arranca en null).
2. `CREATE OR REPLACE VIEW` de `fci_explorador` para incluir `m.patrimonio`.
3. `CREATE OR REPLACE VIEW` de `fci_explorador_grupos`: propagar `patrimonio` a través de las CTEs
   `base`/`best` (mismo tratamiento que `tna`/`rend_updated_at`, que ya viajan por esas CTEs sin
   agregarse entre clases).
4. En `scripts/cafci_sync.py`, dentro de `daily()`: además de construir `rows` para `fci_prices`,
   construir un batch `{id: fci_master_id, patrimonio: <patrimonio_act parseado>}` por fondo
   mapeado (mismo bucle, mismo `idx`) y upsertear por lotes contra `fci_master` (`on_conflict="id"`,
   mismo `BATCH_SIZE`). Parsear `patrimonio_act` con `pd.to_numeric(..., errors="coerce")`; si viene
   NaN, omitir ese fondo del batch de patrimonio (no pisar con null un valor previo bueno por un dato
   malo de un solo día — dejar el valor anterior como está).
5. En `mercadoService.js` / `FciExplorador.jsx`: agregar `'aum': 'patrimonio'` a `SORT_COL` (en
   `getFondosPage`) y una columna nueva con `SortHeader label="AUM" sortK="aum"` siguiendo
   exactamente el mismo patrón que las columnas existentes (`pctCell`/`tnaCell` como referencia de
   estilo, pero un formateador propio para montos grandes — ej. `Intl.NumberFormat` con notación
   compacta, tipo "$ 1.240 M" — no el número crudo sin agrupar).
6. Placeholder claro ('—') cuando `fondo.patrimonio` es `null`/`undefined`.
7. Tests: cubrir el formateador nuevo (casos: null, cero, número grande) y que `SORT_COL.aum` mapea
   a `patrimonio`. Typecheck.

## Fuera de alcance

- Filtro por rango de AUM — este feature es solo persistir + mostrar la columna. Un filtro es
  iteración futura, no confirmada.
- Historizar `patrimonio` en el tiempo (serie temporal, tabla aparte) — solo el valor actual del
  último bulk, mismo criterio que `sociedad_gerente`/`moneda` en `fci_master` hoy.
- Tocar `enrich()`, el modo `--enrich`, o cualquier otro campo de `fci_master` no relacionado con
  patrimonio.
- Modificar el cron (`.github/workflows/cafci_daily.yml`) o dispararlo manualmente.
- AR-031 (liquidez de rescate / comisiones) — feature aparte, no relacionado.

## Restricciones clave

- Migración estrictamente aditiva — nunca borrar ni renombrar columnas existentes de `fci_master`.
- No hacer ~3.974 UPDATEs individuales por corrida del cron — usar upsert por lotes.
- Un dato de patrimonio faltante/no-numérico en un fondo puntual un día dado NO debe pisar el
  último valor bueno con null — mejor "quedó desactualizado" que "se borró".
- `getFondosPage`/`getFondosStats` no deberían necesitar cambios de código — si el planner encuentra
  que sí hacen falta, es señal de que algo del contexto de arriba está desactualizado; revisar antes
  de asumir.
