## Contexto

= S-051 del backlog. Descubierto 2026-09-29 al cerrar F-0065 (Cowork). Diagnóstico verificado contra el código y el historial de git:

1. **Orden equivocado en el loop.** En `index.ts`, `commitStep(step.id, step.desc)` (~línea 571) corre ANTES de `appendAdr(block, state.featureId, step.id)` (~línea 577). `commitStep` hace `stageAll()` = `git add -A` (`git.ts`). Resultado: el ADR del step N queda como cambio sin commitear en `system/DECISIONS.md`.
2. **El reviewer lo ve.** `runReviewer` corre `git diff HEAD` sobre `getRepoRoot()` (`reviewer.ts:28`), sin excluir nada, y trunca a `DIFF_MAX_CHARS = 8000`. Con target sistema, el diff del step N+1 incluye el ADR del step N: el reviewer lo marca como scope-creep, y esas ~14 líneas pueden desplazar código real fuera de lo que llega a ver.
3. **El siguiente `git add -A` lo barre.** Evidencia en git: ADR-0186 (2026-09-21, ADR de Argos/F-0064) quedó dentro del commit del step 1 de F-0065 (`bebe182`), y ADR-0187 dentro del commit del step 9 (`e56f3d1`); ADR-0188 dentro del step 10 (`8f0b00b`). Los ADRs terminan en el commit "equivocado".
4. **Los targets distintos de sistema tienen el problema completo.** `appendAdr` escribe siempre en `system/DECISIONS.md` de augusto-os (`DECISIONS_PATH` fijo en `adr.ts:6`), pero `commitStep` commitea en el repo del target (`getRepoRoot()` viene de `targets.ts`). Con target argos/kredy el ADR no se comitea nunca en el momento y queda esperando a que una corrida de sistema lo barra (eso explica ADR-0186).
5. **PROGRESS.md queda sucio en CADA release.** `appendProgress(path.join(SYSTEM_DIR, 'PROGRESS.md'), ...)` (`index.ts:311`) corre justo después del merge y nadie comitea ese archivo. S-050 resolvió solo BACKLOG.md (`commitAndPushBacklog`).
6. **Anomalía SIN causa confirmada.** En la entrada de PROGRESS de F-0065, ADR-0187 aparece 4 veces (4 steps con `adrIds` que lo contienen), pero `DECISIONS.md` lo tiene una sola vez y el historial (`git log -S`) lo muestra agregado una sola vez. Verificado: `appendAdr` es el único código del orquestador que escribe `DECISIONS.md`, calcula `max+1` leyendo el archivo, y no hay `reset`/`clean`/`stash`/`restore` en el código (solo `checkout` de ramas). No se pudo determinar cómo un mismo ID se asignó a varios steps. **No inventar un fix**: el alcance es instrumentar y dejar un test (ver pasos 5 y 6).

REUSAR:
- `commitAndPushBacklog` y `pushBacklogFile` (`backlog.ts`) — patrón exacto para el commit+push de archivos de sistema en augusto-os: `git add` de archivos puntuales, chequeo de rama default, no-op sin cambios. Sus tests en `backlog.test.ts` (repo git real en tmpdir con remoto bare) son el modelo de los tests nuevos.
- `runReviewer` ya acepta `repoRoot?` y `callClaude?` inyectables (`ReviewerOpts`).
- `appendAdr(draft, featureId, stepId, filePath?)` ya acepta `filePath` para tests.
- `isDirectRun` guard de `index.ts` (ADR-0081): `index.test.ts` ya puede importar sin disparar el CLI.

## Pasos sugeridos (el planner puede refinar)

1. **`reviewer.ts` — excluir archivos de sistema del diff.** Cambiar el comando a `git diff HEAD -- . ':(exclude)system/DECISIONS.md' ':(exclude)system/PROGRESS.md'` (el pathspec positivo `.` es obligatorio para que el exclude funcione). Tests en `reviewer.test.ts` con repo git real en tmpdir: (a) solo cambia `DECISIONS.md` → diff vacío → aprobado sin invocar el modelo; (b) cambia un `.ts` y `DECISIONS.md` → el prompt contiene el `.ts` y no `DECISIONS.md`; (c) repo donde esos archivos ni existen → sin error.
2. **`index.ts` — extraer y reordenar el commit del step.** Extraer de `main()` una función testeable (p. ej. `commitStepWithAdrs`) que: escribe los ADRs pendientes con `appendAdr` (respetando la idempotencia actual `!(step.adrIds?.length)`), guarda los `adrIds` en `STATE.json` de inmediato, y recién entonces llama `commitStep`. Así el commit del step incluye `DECISIONS.md` cuando el target es sistema. Mantener el log `[adr] ADR-XXXX registrado`.
3. **Tests del paso 2** en `index.test.ts` con repo git en tmpdir: (a) tras la función, `git status --porcelain` vacío y `DECISIONS.md` en el commit del step; (b) simular fallo de `commitStep` y re-ejecutar (resume): el ADR existe una sola vez y no se duplica; (c) step sin ADRs pendientes: comportamiento idéntico al actual.
4. **`backlog.ts` (o módulo nuevo) — commit+push de documentos de sistema tras el release.** Función análoga a `commitAndPushBacklog` que comitea y pushea SOLO `system/DECISIONS.md` y `system/PROGRESS.md` en augusto-os (mensaje tipo `chore(system): DECISIONS/PROGRESS tras <featureId>`), con el mismo chequeo de rama default, no-op silencioso si no hay cambios. Invocarla en `index.ts` en la fase de release, junto a `updateBacklogStatus`/`commitAndPushBacklog`, envuelta en try/catch que loguea y NO bloquea el release. Tests contra repo git real en tmpdir con remoto bare: commit+push de los dos archivos, idempotencia (segunda llamada no hace nada), rechazo fuera de la rama default, y que otros archivos sucios NO se incluyen.
5. **`index.ts` — warning por ID de ADR repetido.** Tras `appendAdr`, si el ID devuelto ya figura en `adrIds` de otro step de `state.steps`, loguear `[adr] ID duplicado ADR-XXXX (step A y step B)`. No cambiar el comportamiento, solo instrumentar.
6. **`adr.test.ts` — no-colisión de `appendAdr`.** Llamar `appendAdr` 3 veces seguidas contra un archivo en tmpdir (con la plantilla real de `DECISIONS.md` como fixture): IDs consecutivos y distintos, las 3 entradas presentes, orden newest-first intacto.
7. Typecheck y `npm test` completos.

## Fuera de alcance

- Encontrar o corregir la causa del ADR-0187 repetido en 4 steps: solo se instrumenta (paso 5) y se deja el test de no-colisión (paso 6). Si el test del paso 6 pasa, la causa está fuera de `appendAdr` (hipótesis NO verificada: algo que revierte `DECISIONS.md` sin commitear entre steps, p. ej. el propio builder/fixer); queda como seguimiento aparte.
- Cambiar `commitStep`/`stageAll` (`git add -A`) de forma global, o `DIFF_MAX_CHARS`.
- Mover la generación de ADRs fuera del executor, o cambiar el formato de los ADRs.
- Sospecha aparte, sin verificar: `git diff HEAD` no incluye archivos NUEVOS sin trackear (no hay `git add -N` antes de la revisión en el código), o sea que el reviewer podría no ver archivos nuevos creados por el builder. No se toca acá; verificar por separado.
- Reescribir `commitAndPushBacklog` o alterar su comportamiento actual.
- Notificaciones de Telegram por estos eventos.

## Restricciones clave

- El commit+push de documentos de sistema nunca usa `git add -A`: solo `system/DECISIONS.md` y `system/PROGRESS.md` por ruta explícita, y respeta el chequeo de rama default. Un fallo ahí nunca bloquea el release (el push del target ya pasó).
- El ADR se escribe antes de `commitStep`, pero los `adrIds` se persisten en `STATE.json` antes del commit: un resume tras un fallo de commit no puede duplicar el ADR.
- El pathspec del reviewer debe funcionar aunque `repoRoot` no sea augusto-os (archivos inexistentes en ese repo → sin error).
- Mantener nombres y firmas públicas existentes (`appendAdr`, `runReviewer`, `commitAndPushBacklog`, `commitStep`); los tests actuales dependen de ellos.
- Los tests no pueden pushear a un remoto real: usar repos tmpdir con remoto bare, como `backlog.test.ts`.
- No tocar `state.ts`, `targets.ts` ni `autopilot.ts` salvo que el planner demuestre que hace falta.
- Sin dependencias nuevas.
- Nota de ejecución: F-0066 corre sobre el propio orquestador (target sistema), así que mientras se implementa sigue vigente el comportamiento viejo: es esperable que sus propios ADRs aparezcan en el diff del reviewer hasta que se mergee.
