## Mapa del repo para: tres-saltenas — Retiros sin tope de saldo + no se puede borrar una carga hecha por error

**Resumen:** El repo tres-saltenas es una app Next.js con tRPC, Prisma/PostgreSQL y Clerk para gestionar una producción de empanadas. El modelo Retiro no tiene ninguna validación contra el saldo disponible — se puede retirar cualquier monto sin restricción. No existe ningún procedimiento delete (ni soft-delete, ni undo) en ningún router del sistema: compras, retiros, ventas, gastos y lotes son irreversibles una vez creados. Implementar estas funcionalidades requerirá agregar procedimientos delete en los routers tRPC correspondientes (con wrappers de transacción para revertir efectos secundarios como stockActual) y posiblemente persistir el saldo o agregar validación previa en retiro.create.

## Riesgos y restricciones técnicas para: tres-saltenas — Retiros sin tope de saldo + no se puede borrar una carga hecha por error

**Resumen:** El sistema no tiene ningún mecanismo server-side que limite los retiros según el saldo disponible del negocio — solo hay una alerta cliente-side débil (window.confirm por montos > $50.000). Además, no existe ningún procedimiento delete ni update en el router de retiros, por lo que una carga errónea es irreversible vía API. Si se implementara borrado de retiros, el impacto es acotado (solo afecta el aggregate de saldoNegocio, que se recalcula automáticamente), pero habría que crear tests nuevos y extender los mocks existentes. El mayor riesgo de deuda técnica sería replicar un patrón de delete sin considerar que otras entidades (compra, lote) tienen efectos colaterales en transacciones (stock, costo unitario) que sí requerirían migraciones complejas.

- Validar inputs con zod (z.object, z.number().positive(), z.date())
- Usar ctx.db.$transaction para operaciones que afectan múltiples tablas

### Riesgos / Restricciones
- RETIROS SIN TOPE DE SALDO: El procedimiento create en retiro.ts solo valida monto > 0 con zod. No existe ninguna verificación del lado servidor de que el saldo del negocio (ingresos - compras - gastos - retiros acumulados) sea suficiente para cubrir el retiro. La única alerta es un window.confirm cliente-side (MONTO_ALERTA = 50000) que no es vinculante.
- NO HAY DELETE NI UPDATE EN RETIROS: El router retiro.ts solo expone create, list y byPeriod. No existe ningún procedimiento delete o update. Si se carga un retiro erróneo, no hay forma de corregirlo vía API. Tampoco hay UI de borrado en retiros/page.tsx.
- EFECTO COLATERAL EN saldoNegocio: dashboard.ts calcula el saldo como ingresos - compras - gastos - retiros, sumando TODOS los retiros con aggregate({ _sum: { monto: true } }) sin filtro temporal. Si se implementara borrado de retiros, el saldo se recalcula automáticamente (comportamiento correcto), pero si se implementara borrado de compras o lotes (que usan $transaction con descuento de stock y actualización de costoUnitarioActual), habría que hacer una migración compleja para revertir esos efectos.
- INCONSISTENCIA saldoNegocio vs byPeriod: saldoNegocio suma retiros de TODOS los períodos (sin filtro), mientras que byPeriod acepta desde/hasta. No hay un saldo por período disponible, lo que podría confundir si se muestran ambos.
- TESTS EXISTENTES NO CUBREN DELETE: retiro.test.ts solo testea create, list y byPeriod. saldo.test.ts testea calcularSaldoNegocio y dashboardRouter.saldoNegocio. Si se agrega delete, hay que crear tests nuevos. No hay tests de integración que verifiquen la consistencia del saldo tras operaciones de borrado.
- DEUDA TÉCNICA: costoUnitarioActual de Insumo se actualiza con cada compra (precioTotal / cantidad, no promedio ponderado). Al borrar una compra, el costo unitario quedaría desactualizado porque no hay recálculo. Similar para stockActual que se incrementa en cada compra y se descuenta en cada lote.
