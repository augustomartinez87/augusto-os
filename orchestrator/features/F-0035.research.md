## Riesgos y restricciones técnicas para: tres-saltenas — Agregar insumo nuevo desde /insumos

**Resumen:** Para agregar 'Crear insumo nuevo' desde /insumos hay que: (1) agregar un procedimiento 'create' en insumoRouter siguiendo el patrón de compraRouter.create con validación zod, (2) crear un formulario de alta en src/app/insumos/page.tsx, (3) invalidar insumo.list tras la creación para que compras refleje el cambio. Los principales riesgos son la falta de constraint de unicidad en nombre del insumo (riesgo de duplicados), la ausencia de restricción enum en unidad (validación solo a nivel de aplicación), y la necesidad de agregar tests tanto unitarios (create) como de auth (procedimiento protegido) para mantener la cobertura actual.

### Riesgos / Restricciones
- El modelo Insumo en Prisma no tiene constraint de unicidad en `nombre` — se podría crear el mismo insumo dos veces si no se agrega validación
- El campo `unidad` se define como String libre en Prisma (solo comentado como 'kg' | 'unidad') — no hay restricción a nivel BD. Si se crea un insumo con otra unidad, rompería supuestos en compras y recetas
- No existe página ni formulario de alta en /insumos — la UI debe crearse desde cero siguiendo el patrón de compras/gastos
- Al crear un insumo, hay que invalidar la query 'insumo.list' para que el dropdown de compras se actualice. Olvidar esto rompe la UX de compras
- Los tests de auth (src/__tests__/auth.test.ts) listan procedimientos protegidos explícitamente. Si se agrega 'insumo.create' como protectedProcedure, habría que agregarlo también a esa lista de tests para mantener cobertura
- La query 'insumo.list' actualmente selecciona solo ciertos campos (id, nombre, unidad, stockActual, stockMinimo, costoUnitarioActual). Si el nuevo create modifica la proyección, podría impactar las páginas que consumen este endpoint
- Posible deuda técnica: no hay un tipo enum compartido para 'unidad' — está comentado en el schema pero no tipado fuertemente. Se sugiere crear un tipo zod enum para validación server-side
