## Contexto

F-0037 agregó el bloque de "Comisión total"/"Por cuota" en `CarteraTab` (`app/ap/page.tsx`), pero
depende 100% de `loan.commissionExpected` (= `Number(comm.expectedCommission ?? 0)`, `server/routers/ap.ts:2193`),
que solo se completa en el flujo normal de preaprobación (`expectedCommission: pa.totalCommission` al
crear el loan, línea 773). Existe un segundo flujo — **asignación retroactiva de un AP a un préstamo
ya existente** (`server/routers/ap.ts` ~línea 1995-2046, metadata `retroAssigned: true`) — que crea
el `ApCommission` con `expectedCommission: null` **a propósito** (no hubo simulación previa, el
préstamo ya estaba desembolsado), pero SÍ setea `loan.apCommissionRatio` cuando `ratio > 0` (ver
`if (ratio > 0) { await tx.loan.update(...) }` justo después, línea ~2048). Confirmado en vivo por
Augusto (2026-07-28): de 3 préstamos en su "Mi cartera", solo el que pasó por preaprobación normal
mostró el bloque nuevo — los otros dos no, aunque son préstamos reales con comisión.

El motor real de liquidación (`server/services/commission.service.ts::realizeCommissionsForPayment`,
línea 69-155) calcula, por cada cuota efectivamente cobrada: `commission = cashflowAmount(componentes
'principal'+'interest_current' de ese pago) × apCommissionRatio` (línea 114-115). Kredy usa
amortización francesa (cuota fija) — así que el total esperado de comisión de un préstamo con ratio
fijo se puede aproximar, SIN journal replay del motor real, como `apCommissionRatio × Σ(loanInstallments.amount)`
sobre TODAS las cuotas del préstamo (pagadas + pendientes) — evitar `capital × ratio`, que
subestimaría (el capital no incluye interés) o sobre/subestimaría según la estructura del préstamo.

## Pasos sugeridos (el planner puede refinar)

1. En `server/routers/ap.ts`, dentro de `apMyPortfolio` (~línea 2125-2197): extender el `select` de
   `ctx.prisma.loan.findMany` (~línea 2153-2167) para incluir `apCommissionRatio: true` (ya existe en
   el modelo `Loan`, columna `apCommissionRatio DECIMAL(8,6)` — ver migración `20260610150000_ap_commission_ledger`).
2. En el mapeo final (~línea 2171-2196): cuando `comm.expectedCommission` sea null/undefined Y
   `loan.apCommissionRatio` sea > 0, calcular `commissionExpected` como
   `Number(loan.apCommissionRatio) × installments.reduce((sum, i) => sum + Number(i.amount), 0)`
   (usar `decimal.js` para la multiplicación si el archivo ya lo usa en otro lado de este router,
   para consistencia de redondeo — revisar imports existentes). Si `comm.expectedCommission` SÍ
   existe, usarlo tal cual (no reemplazar el valor real por el fallback). Si `apCommissionRatio` es
   null/0, `commissionExpected` queda en 0 como hoy — sin cambios de comportamiento para ese caso.
3. No tocar `app/ap/page.tsx` — el frontend ya consume `loan.commissionExpected` desde F-0037, así
   que el fix resuelto en el backend alcanza para que el bloque aparezca solo con el cambio del paso 2.
4. Tests: extender los tests existentes del router (o de `apMyPortfolio` si tiene archivo propio)
   cubriendo: (a) préstamo con `expectedCommission` guardado → se usa ese valor, no el fallback;
   (b) préstamo con `expectedCommission` null y `apCommissionRatio > 0` → se calcula el fallback
   correctamente contra una suma de cuotas conocida; (c) préstamo con `apCommissionRatio` null/0 →
   `commissionExpected` sigue en 0, sin excepción ni NaN.
5. Typecheck, lint y tests.

## Fuera de alcance

- No tocar `realizeCommissionsForPayment` ni el motor real de liquidación de comisión — el fallback
  es solo para MOSTRAR un estimado antes de que se cobre nada, la liquidación real sigue cuota a cuota
  igual que siempre.
- No persistir el fallback calculado en `ApCommission.expectedCommission` ni en ningún campo nuevo —
  se calcula al vuelo en cada request de `apMyPortfolio`, nunca se escribe.
- No diferenciar visualmente "exacto" vs. "estimado" en el frontend — fuera de alcance de esta
  iteración (se puede sumar después si hace falta).
- No tocar el flujo de asignación retroactiva en sí (líneas 1995-2050) — solo el consumo de sus datos
  en `apMyPortfolio`.

## Restricciones clave

- Nunca exponer `apCommissionRatio` (la tasa) directamente al AP — solo montos absolutos ya calculados,
  igual que F-0037.
- El fallback debe ser current (no cachear un valor viejo) — se recalcula en cada llamada a
  `apMyPortfolio`, consistente con que `loanInstallments` puede cambiar (refinanciación, etc.).
- Sin migración de schema — `apCommissionRatio` ya existe en `Loan`, no se agrega ningún campo nuevo.
