## Contexto

El backend YA soporta cualquier plazo. En `server/routers/ap.ts` los tres endpoints relevantes
validan `termMonths: z.number().int().min(1).max(360)` (líneas 233, 308 y 355) — no hay ninguna
restricción a los presets del lado del servidor. La limitación es puramente del frontend.

En `app/ap/page.tsx`, el plazo se elige con una grilla de botones construida desde `config.terms`
(líneas ~699-711):

```tsx
<div className="grid grid-cols-4 gap-2">
  {config.terms.map(t => (
    <button key={t} onClick={() => setSelectedTermMonths(t)}
      className={cn('py-3 rounded-xl border text-sm font-bold transition-all',
        selectedTermMonths === t
          ? 'bg-blue-600/20 border-blue-500/50 text-blue-300'
          : 'bg-white/3 border-white/8 text-zinc-400 hover:bg-white/6')}>
      {t}m
    </button>
  ))}
</div>
```

El estado es `selectedTermMonths` (inicializado en la línea ~395 con `config.terms[0] ?? 6`) y se
pasa tal cual a la simulación en la línea ~455:

```tsx
const res = await simulateMut.mutateAsync({ token, capital: capitalNum, termMonths: selectedTermMonths, grossTna })
```

La tasa efectiva ya es función del plazo: `grossTnaForTerm(termMonths)` (línea ~423) llama a
`getTermAdjustment(termMonths)` (línea ~408), que busca el rango `minMonths <= t <= maxMonths` en la
config. Eso funciona con cualquier número — no hay que tocarlo, solo asegurarse de que el plazo
custom pase por el mismo camino y no por un atajo nuevo.

Motivo del pedido: los presets cubren los casos típicos, pero cuando se pacta un plazo distinto con
el cliente hay que pedirle a un dev que toque la config, para algo que el backend ya acepta.

## Pasos sugeridos (el planner puede refinar)

1. Agregar estado local para el modo custom: un booleano (ej. `useCustomTerm`) y el texto crudo del
   input (ej. `customTermMonths`, como string, para poder distinguir "vacío" de "0" mientras el
   usuario tipea). Seguir el patrón que el archivo ya usa para la tasa custom (`useCustomRate` /
   `customGrossTna`, línea ~426) — misma forma, misma nomenclatura.
2. Agregar el botón "Otro" al final de la grilla de plazos, con el mismo tratamiento visual activo/
   inactivo que los presets. Al tocarlo, activa el modo custom y revela el input numérico debajo de
   la grilla.
3. Derivar `selectedTermMonths` del input cuando el modo custom está activo, validando entero entre
   1 y 360. Mientras el valor sea inválido o el input esté vacío, no actualizar el plazo efectivo y
   dejar el botón de simular deshabilitado con un mensaje corto de por qué (mismo tono y estilo que
   los mensajes de error ya presentes en la pantalla).
4. Al tocar un preset, salir del modo custom y limpiar el input, para que no queden los dos estados
   activos a la vez.
5. Verificar que `grossTnaForTerm(selectedTermMonths)` se siga llamando con el plazo efectivo (custom
   o preset) sin ninguna rama especial — si hace falta una rama, es señal de que el plazo custom no
   está entrando por el camino normal.
6. Agregar tests de la lógica de validación del plazo custom (entero, rango 1-360, vacío) siguiendo
   el estilo de los tests existentes del router/UI de AP.
7. Correr typecheck, lint y tests, y corregir lo que rompa.

## Fuera de alcance

- El flujo de compartir plazos por WhatsApp (`shareSelected` / `termSims`, líneas ~507-527) sigue
  operando solo sobre `config.terms`. Sumar plazos custom al comparador compartible es otra feature.
- Cambiar `config.terms` o agregar una UI para administrar los presets.
- Tocar la validación del backend — ya acepta 1..360, no hay nada que ampliar ahí.
- Persistir el último plazo custom usado entre sesiones.

## Restricciones clave

- Sin migración de schema ni cambios en la base — es solo frontend.
- La TNA/tasa NUNCA debe mostrarse en vistas de prestatario. Esta pantalla es del AP, así que la
  tasa puede verse, pero no agregar ninguna exposición de tasa nueva más allá de lo que ya hay.
- No romper el flujo de presets: es el camino que se usa el 90% de las veces y tiene que quedar
  exactamente igual de rápido (un tap).
- Respetar el sistema visual existente de `/ap` (clases `bg-white/3`, `border-white/8`,
  `bg-blue-600/20`, etc.). No introducir un componente de input con otro estilo.
