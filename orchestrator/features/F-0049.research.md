## Identificar riesgos y restricciones técnicas para implementar la 'franja de referencia (caución propia)' y los 'KPIs del universo filtrado' en el Explorador de FCI (Argos FCI).

**Resumen:** El Explorador de FCI consume vistas de Supabase exclusivamente vía mercadoService.getFondosPage (paginado con count:'exact') y normaliza filas con normalizeFondo, apoyándose en constantes centralizadas en features/fci/constants.js. La 'franja de referencia (caución propia)' no tiene ninguna infraestructura de datos previa en el repo (no existe tabla/serie de caución; el único TODO de benchmarks lista CER/UVA/IPC/MEP_GD30/A3500), por lo que requerirá fuente de datos y migración nueva aplicada a mano con bloque ROLLBACK. Los 'KPIs del universo filtrado' chocan con la paginación server-side: no hay agregación disponible (la vista 039 solo expone n_clases y clases_hermanas JSONB), exigen una query agregada separada que replique exactamente los filtros y el filtro stale acoplado a getLatestUniverseDate sobre fci_explorador. Riesgos principales: romper los tests que mockean la cadena fluente de Supabase, dependencia de la migración manual 039 no verificada en cada entorno (default groupByFund=true apunta a la vista), y costo de performance de count:'exact' más una segunda query sobre JSONB_AGG. ### Riesgos / Restricciones
- No existe en el repo ninguna serie de datos de 'caución propia' ni tabla de referencia. El único TODO forward-compat de benchmarks (constants.js) lista series CER, UVA, IPC_MES, MEP_GD30, A3500 — sin caución. La franja de referencia requerirá una fuente de datos nueva y probablemente una migración nueva.
- Los KPIs 'del universo filtrado' no tienen agregación server-side: getFondosPage usa select('*', { count: 'exact' }) con .range() paginado (PAGE_SIZE=50). Calcular KPIs sobre TODO el universo filtrado exige una query agregada separada; hacerlo client-side sobre la página daría KPIs incorrectos (solo 50 filas).
- Coupling con el filtro stale: getLatestUniverseDate() consulta SIEMPRE fci_explorador (vista plana) y el resultado se aplica como .gte(STALE_DATE_FIELD, universeDate) tanto en modo plano como en modo grupo; en modo grupo filtra por rend_updated_at de la clase representativa, no de todas las clases — puede excluir grupos legítimos.
- La vista fci_explorador_grupos (migration 039) NO expone columnas de agregado KPI (solo n_clases y clases_hermanas JSONB). Añadir KPIs de grupo requiere ampliar la vista o agregar aparte.
- groupByFund default es true en el front, que apunta a fci_explorador_grupos. Si la migración 039 no se aplicó en el entorno (migración manual, sin CI/CD), getFondosPage fallará con error de tabla inexistente → riesgo de 500 al cargar el Explorador.
- La heurística de agrupamiento (REGEXP_REPLACE del sufijo 'Clase X') puede dejar fondos_base mal agrupados si un nombre no sigue el patrón; el override fci_class_overrides empieza vacío y requiere carga manual de admin → riesgo de datos inconsistentes en KPIs por grupo.
- Los tests existentes (mercadoService.getFondosPage.test.js) asertan la cadena fluente exacta de Supabase (.eq, .or, .gte, from('fci_explorador_grupos'/'fci_explorador') y 'sin filtros opcionales no llama .eq ni .or'). Agregar una query agregada o filtros nuevos romperá estos tests y el mock builder (makeBuilder) si se añaden métodos no soportados.
- count: 'exact' sobre una vista con JSONB_AGG y DISTINCT ON es costoso en performance; sumar una segunda query de KPIs sobre el mismo universo agrava el costo.
- Convención de casing: el componente de KPI es KpiCard.jsx (no KPICard); usarlo mal rompe el import.
- El filtro search usa .or(`nombre.ilike...`) sobre la vista; KPIs del universo filtrado deberán replicar exactamente el mismo conjunto de filtros (moneda, clasificacion_cod, sociedad_gerente, search, stale) o divergirán de la tabla.
