## Investigar qué existe para implementar: tres-saltenas — Forzar autenticación real (middleware + tRPC), hoy no protege nada

**Resumen:** El proyecto tiene Clerk instalado y configurado (middleware + ClerkProvider + páginas sign-in/sign-up), pero la capa tRPC no protege NADA: todas las procedures son publicProcedure, el contexto createTRPCContext no recibe req ni extrae auth, y ningún endpoint verifica el usuario. Para implementar autenticación real hay que (1) modificar createTRPCContext para recibir CreateContextOptions y llamar a auth() de @clerk/nextjs/server para obtener userId, (2) crear un authedProcedure que use t.middleware para verificar userId y lanzar TRPCError UNAUTHORIZED si falta, y (3) reemplazar publicProcedure por authedProcedure en todos los endpoints de los 9 routers.

### Riesgos / Restricciones
- createTRPCContext no recibe parámetros (es async () => ... ), por lo que no puede acceder al objeto req de Clerk. Habrá que cambiar su firma a async (opts: CreateContextOptions) para recibir req y extraer auth con auth() de @clerk/nextjs/server.
- TODAS las procedures (9 routers ≈ 18 endpoints) usan publicProcedure. Habrá que crear un authedProcedure que verifique auth en el contexto y reemplazar publicProcedure por authedProcedure en cada endpoint que requiera protección.
- El middleware de Clerk ya está activo, pero no bloquea llamadas tRPC sin sesión — solo las pages. La protección real debe estar en el contexto tRPC y en las procedures.
- No existe ningún throw con TRPCError code UNAUTHORIZED ni FORBIDDEN en ningún router.

## Riesgos y restricciones técnicas para: tres-saltenas — Forzar autenticación real (middleware + tRPC), hoy no protege nada

**Resumen:** El repo tiene Clerk instalado y configurado en la UI (layout con ClerkProvider, sign-in/sign-up pages), pero **ninguna protección del lado servidor**: middleware.ts corre clerkMiddleware vacío sin auth.protect(), y los 9 routers tRPC (compra, insumo, producto, lote, venta, gasto, retiro, config, dashboard) usan exclusivamente publicProcedure sin verificar sesión. El principal riesgo técnico es que agregar auth al contexto tRPC romperá los 7 archivos de tests existentes, que crean callers con `{ db } as any` sin mockear auth. Además, hay que decidir si la protección se implementa a nivel middleware (global en rutas) o a nivel tRPC (protectedProcedure), o ambos, y definir qué procedimientos pueden seguir siendo públicos (si corresponde).

### Riesgos / Restricciones
- Todos los tests existentes (7 archivos) usan createCallerFactory con { db } as any sin auth. Si se agrega auth al contexto tRPC, TODOS rompen y requieren mockear auth() en cada test suite.
- createTRPCContext actualmente solo devuelve { db }. Clerk auth() necesita headers() en server components, lo que acopla el contexto al runtime de Next.js y puede complicar tests.
- middleware.ts no tiene auth.protect() — ClerkMiddleware corre pero no bloquea nada. Cualquiera sin sesión accede a todas las rutas y procedimientos tRPC.
- Todos los 9 routers (compra, insumo, producto, lote, venta, gasto, retiro, config, dashboard) usan exclusivamente publicProcedure. No hay distinción entre rutas públicas y protegidas: hay que revisar una por una si deben ser protegidas o no.
- El matcher de middleware.ts cubre /(api|trpc)(.*) — si se agrega protect() global, también afectará endpoints que quizás deban ser públicos. Requiere matcher granular.
- Hay página de sign-up pública (/sign-up) — SESSION-HANDOFF.md advierte que cualquiera con el link puede registrarse. Hay que deshabilitar signup público en dashboard de Clerk.
- La tRPC route handler (route.ts) no inyecta auth en el contexto. Clerk auth() debe llamarse ahí o en createTRPCContext, pero al ser un fetch handler (edge), requiere manejo cuidadoso de headers.
- Riesgo de que el ejecutor automático intente modificar middleware.ts sin coordinación (documentado en SESSION-HANDOFF.md gotcha #8).
