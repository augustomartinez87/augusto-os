## Contexto

En `src/features/portfolio/components/strategy/StrategyTab.jsx` (líneas 7-21), la distribución
objetivo de estrategias vive enteramente en `localStorage`:

```jsx
const TARGETS_KEY = 'portfolio_strategy_targets';
const DEFAULT_TARGETS = { core1: 50, core2: 30 };

export function StrategyTab({ positions, totals, currency = 'ARS' }) {
  const [targets, setTargets] = useState(() => {
    try {
      const stored = localStorage.getItem(TARGETS_KEY);
      return stored ? JSON.parse(stored) : DEFAULT_TARGETS;
    } catch {
      return DEFAULT_TARGETS;
    }
  });

  useEffect(() => {
    localStorage.setItem(TARGETS_KEY, JSON.stringify(targets));
  }, [targets]);
  ...
  <TargetAllocation ... targets={targets} onChangeTargets={setTargets} ... />
```

`targets` se pasa a `<TargetAllocation onChangeTargets={setTargets} />`, que es quien dispara los
cambios cuando el usuario edita los porcentajes. Augusto usa la app desde más de un dispositivo, y
hoy la distribución configurada en uno no aparece en el otro.

**No existe hoy ninguna tabla en Supabase para configuración por usuario editable por el propio
usuario.** La candidata obvia, `user_profiles` (tiene precedente de guardar JSON por usuario en la
columna `modules`, ver `supabase/migrations/009_user_roles_system.sql` línea 13), tiene su política
de `UPDATE` restringida a admins (`"Admins can update all profiles" ... USING (public.is_admin())`,
misma migración línea 74-75) — un usuario normal no puede escribir su propia fila hoy. Por eso este
feature necesita una tabla nueva y chica, dedicada solo a esto, en vez de extender la RLS de
`user_profiles` (evita tocar la política de admin/roles).

**Migración a aplicar a mano ANTES de correr este feature** (ver Restricciones clave — el loop NO
la ejecuta, solo puede escribir el archivo):

```sql
-- supabase/migrations/038_user_strategy_targets.sql
CREATE TABLE IF NOT EXISTS user_strategy_targets (
  user_id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  targets JSONB NOT NULL DEFAULT '{"core1": 50, "core2": 30}'::jsonb,
  updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

ALTER TABLE user_strategy_targets ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users manage own strategy targets" ON user_strategy_targets
  FOR ALL USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id);

DROP TRIGGER IF EXISTS update_user_strategy_targets_updated_at ON user_strategy_targets;
CREATE TRIGGER update_user_strategy_targets_updated_at
  BEFORE UPDATE ON user_strategy_targets
  FOR EACH ROW EXECUTE FUNCTION public.update_updated_at_column();
```

(`public.update_updated_at_column()` ya existe — la crea `009_user_roles_system.sql`, reusada por
varias tablas del proyecto.)

Para leer el usuario actual: `useAuth()` desde `@/features/auth/contexts/AuthContext` expone
`user` (con `user.id`) — mismo patrón que ya usa `src/features/portfolio/contexts/PortfolioContext.jsx`
línea 4 y 22. Para el cliente de Supabase: `import { supabase } from '@/lib/supabase'` (mismo import
que `userService.js`).

## Pasos sugeridos (el planner puede refinar)

1. Confirmar que la migración `038_user_strategy_targets.sql` ya fue aplicada a la base (el guard
   del loop nunca la corre solo; si la tabla no existe, los pasos siguientes van a fallar en
   tests/typecheck de forma esperable — avisar y detenerse, no simular ni mockear la tabla como si
   existiera).
2. Crear un hook nuevo, p.ej. `src/features/portfolio/hooks/useStrategyTargets.js`, que: al montar,
   si hay `user.id`, hace `supabase.from('user_strategy_targets').select('targets').eq('user_id', user.id).maybeSingle()`;
   si no hay fila (usuario nuevo) o falla, devuelve `DEFAULT_TARGETS`; expone `{ targets, setTargets, loading, saveError }`.
3. `setTargets` del hook actualiza el estado local de inmediato (UI optimista) y dispara un
   `upsert` a `user_strategy_targets` con `{ user_id, targets }`; si el upsert falla, exponer el
   error vía `saveError` sin revertir el valor local (el usuario sigue viendo lo que tipeó).
4. Reemplazar en `StrategyTab.jsx` el `useState`/`useEffect` de `localStorage` (líneas 7-21) por
   este hook nuevo. Sacar `TARGETS_KEY` y el `localStorage.getItem`/`setItem` — no dejar los dos
   mecanismos conviviendo.
5. Mostrar el estado de carga (`loading`) de forma simple mientras se resuelve el fetch inicial —
   seguir el patrón visual ya usado en otras partes de Argos para estados de carga (buscar
   `Skeleton` o spinners ya existentes en `src/components/ui` antes de inventar uno nuevo).
6. Si `saveError` está seteado, mostrar un aviso corto y no bloqueante (similar en tono a los
   mensajes de error ya usados en la UI de Argos) — no usar `alert()`/`confirm()`.
7. Tests: mockear `supabase.from` (buscar cómo se mockea Supabase en tests ya existentes del
   proyecto, si los hay, antes de inventar el mock) y cubrir: (a) fetch inicial devuelve la fila
   guardada; (b) sin fila, usa `DEFAULT_TARGETS`; (c) editar dispara upsert con el `user_id`
   correcto; (d) upsert fallido no revierte el valor local y expone el error.
8. Correr typecheck, lint y tests, y corregir lo que rompa.

## Fuera de alcance

- `TradeJournal.jsx` (línea ~223) tiene el mismo patrón de `localStorage` para las entradas del
  diario de trading — es un problema análogo pero NO está trackeado como parte de `AR-006` en el
  backlog. No tocarlo en este feature.
- Migrar datos ya guardados en `localStorage` de usuarios existentes hacia la DB — si Augusto tenía
  una distribución custom guardada localmente, se pierde y vuelve al default al primer load con
  este feature. Aceptable dado el volumen de usuarios (Augusto es prácticamente el único).
- Sincronización en tiempo real entre pestañas/dispositivos abiertos simultáneamente (websockets/
  realtime de Supabase) — alcanza con que el valor correcto se vea al cargar/recargar la pantalla.
- Cualquier cambio a `RebalanceAlerts` más allá de que siga recibiendo `targets` con la misma forma
  que hoy (`{ core1, core2 }`).

## Restricciones clave

- **Toca DB → gate humano requerido antes de correr la migración.** El loop NUNCA debe aplicar
  `supabase/migrations/038_user_strategy_targets.sql` a la base en vivo ni correr SQL contra la DB
  real — solo puede escribir el archivo si hace falta reescribirlo. Augusto aplica la migración a
  mano (Supabase SQL editor o CLI) antes de que este feature pueda funcionar de punta a punta.
- No extender ni modificar la RLS de `user_profiles` — la tabla nueva es deliberadamente aislada
  para no tocar la política de admin/roles existente.
- Sin librerías nuevas de data-fetching (nada de agregar react-query a este flujo si el resto de
  `features/portfolio` no lo usa ya de forma establecida — confirmar antes de sumar una dependencia
  nueva al patrón).
- No renombrar ni cambiar la forma del objeto `targets` (`{ core1, core2 }`) — `RebalanceAlerts` y
  `TargetAllocation` ya lo consumen con esa forma.
