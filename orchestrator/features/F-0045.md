## Contexto

Hoy, cuando el AP pre-aprueba un préstamo para un cliente nuevo (sin Person previa), la Person que
se crea SIEMPRE queda con `relationship: 'conocido'` (default de schema, `prisma/schema.prisma`
línea 83) y `referrer: null` — el AP no tiene forma de indicar si conoce poco a esa persona o quién
se la refirió. El único lugar donde `relationship`/`referrer` se puede editar hoy es el dashboard de
Augusto (`app/dashboard/persons/page.tsx`, `PersonFormDialog`, líneas 800-928) — el AP no tiene
acceso a esa pantalla (opera sin sesión Clerk, vía token, ver `AgentConfig.token` y `SP-014`).

Esto importa porque `relationship` es el input central del gate de límite por vínculo (F-0005,
`server/services/relationshipLimit.ts`, `checkRelationshipLimit`): "conocido"/"amigo" habilitan
hasta $500.000, "amigo_de_amigo" hasta $200.000 (y requiere `referrer` o queda en revisión manual),
"desconocido" limita a $0. Como HOY nunca se guarda otra cosa que no sea el default 'conocido', el
gate nunca ve una Person nueva como "amigo_de_amigo" ni "desconocido" — corre siempre con el tier
más permisivo por default silencioso, sin que Augusto se entere de qué cree el AP sobre esa
relación. Dar el campo explícito no reduce seguridad respecto de hoy (el default actual ya es más
permisivo que casi cualquier elección real) — la mejora es reemplazar un default ciego por una
elección visible y auditable.

**Dónde vive `preApprove` hoy** (`server/routers/ap.ts`, mutation `preApprove`, input en líneas
348-360): NO tiene campos de `relationship`/`referrer`. Dentro de la transacción (línea ~538-551),
la Person se resuelve así:

```ts
let resolvedPersonId: string | null = null
if (normalizedCuil) {
  const identityResult = await resolvePerson(tx, config.userId, contact.id, normalizedCuil)
  resolvedPersonId = identityResult.borrowerId
}
if (!resolvedPersonId) {
  const nameResolve = await resolvePersonByIdentity(tx, config.userId, {
    cuil: normalizedCuil, name: input.clientName, create: true,
  })
  resolvedPersonId = nameResolve.personId
  ...
}
```

`resolvePerson` (`server/services/identity.service.ts`) **nunca crea una Person** — si no encuentra
match devuelve `action: 'created', borrowerId: null` (nombre engañoso: es una señal de "no hay
match", la creación real pasa a otro lado) o `action: 'linked_existing'` si ya existía. La Person se
crea de verdad únicamente dentro de `resolvePersonByIdentity` (`lib/identity/resolvePerson.ts`,
líneas 97-107, rama `if (create)`), que hoy hace:

```ts
const created = await db.person.create({
  data: { userId, name: opts.name ?? 'Sin nombre', cuit: opts.cuil ?? undefined,
          identityStatus: opts.cuil ? 'verified' : 'pending' },
  select: { id: true },
})
return { personId: created.id, matchedBy: 'created', warnings }
```

`resolvePersonByIdentity` también devuelve `matchedBy: 'cuil' | 'dni' | 'name'` cuando encontró una
Person EXISTENTE — esa es la señal para saber si corresponde escribir `relationship`/`referrer` o
no (solo en `matchedBy === 'created'`).

**Patrón de UI a copiar** — el selector de relación ya existe en el dashboard de Augusto
(`app/dashboard/persons/page.tsx` líneas 915-923), con las mismas 3 opciones que acepta el schema
(`amigo` | `amigo_de_amigo` | `conocido` — 'desconocido' no es una opción elegible, es el fallback
de `checkRelationshipLimit` cuando no hay dato):

```tsx
<Select value={relationship} onValueChange={setRelationship}>
  <SelectTrigger><SelectValue /></SelectTrigger>
  <SelectContent>
    <SelectItem value="amigo">Amigo</SelectItem>
    <SelectItem value="amigo_de_amigo">Amigo de amigo</SelectItem>
    <SelectItem value="conocido">Conocido</SelectItem>
  </SelectContent>
</Select>
```

`Select`/`SelectTrigger`/`SelectContent`/`SelectItem` ya están importados en `app/ap/page.tsx`
(línea 11-13, usados en el diálogo de "Marcar como perdido", línea 181) — no hace falta agregar el
import, pero ESE uso es dentro de un `Dialog` con tema claro. El paso `confirm` donde van estos
campos nuevos (líneas ~798-838) tiene su propio estilo oscuro custom (inputs con ícono +
`bg-white/5 border border-white/10 rounded-2xl ...`, ver el input de `clientData.purpose` línea
822-826) — los campos nuevos deben visualmente encajar ahí, no traer el look claro del otro uso de
`Select` en este mismo archivo.

## Pasos sugeridos (el planner puede refinar)

1. En `lib/identity/resolvePerson.ts`, extender el tipo de `opts` de `resolvePersonByIdentity` con
   `relationship?: 'amigo' | 'amigo_de_amigo' | 'conocido' | null` y `referrer?: string | null`, y
   en la rama `if (create)` (líneas ~97-104) pasarlos a `db.person.create` como
   `relationship: opts.relationship ?? undefined, referrer: opts.referrer ?? undefined` (con
   `undefined` el default de schema `'conocido'` se sigue aplicando igual que hoy cuando no se
   pasa nada — no cambia el comportamiento de ningún otro caller existente de esta función).
2. En `server/routers/ap.ts`, agregar al input de `preApprove` (líneas 348-360)
   `relationship: z.enum(['amigo', 'amigo_de_amigo', 'conocido']).optional()` y
   `referrer: z.string().max(200).optional()` — mismos valores que ya usa `server/routers/persons.ts`
   línea 14 para el mismo campo, sin `.default()` (necesitamos poder distinguir "no eligió nada" de
   un valor).
3. En el mismo archivo, en la llamada a `resolvePersonByIdentity` dentro de la tx (línea ~544),
   pasar `relationship: input.relationship, referrer: input.referrer || undefined`. NO tocar la
   rama de `resolvePerson` (identity.service.ts) — esa función nunca crea la Person, así que no hay
   nada que setear ahí.
4. En `app/ap/page.tsx`: agregar `relationship` y `referrer` (ambos opcionales) a la interfaz
   `ClientData` (línea 97) y al estado inicial (línea 375); en el paso `confirm` (después del input
   de `cbu`, antes del botón "Pre-aprobar", ~línea 830), agregar los dos campos nuevos como sección
   claramente opcional (ej. un subtítulo tipo "¿Conocés a este cliente? (opcional)") para no romper
   la promesa de copy actual "Solo necesito 3 datos para mandárselo a Augusto" (línea 805) como algo
   obligatorio — actualizar ese texto si hace falta para que siga siendo honesto con 5 campos en
   pantalla, 3 obligatorios + 2 opcionales. Pasar ambos valores en la llamada a
   `preApproveMut.mutateAsync` (línea ~475-481).
5. Tests: (a) en `resolvePersonByIdentity` — Person nueva sin `relationship`/`referrer` en el input
   sigue creándose con los defaults de siempre (`conocido`/`null`, sin regresión); Person nueva CON
   `relationship`/`referrer` en el input los persiste tal cual. (b) en `ap.preApprove` (o el nivel
   que corresponda según cómo estén mockeados los tests existentes de este router) — una Person que
   ya existía (matcheada por CUIL) mantiene su `relationship` original sin importar qué mande el AP
   en el input nuevo. Buscar cómo se mockea Prisma/tx en los tests ya existentes de `ap.ts`
   (`tests/ap-*.test.ts`, `tests/debtor-exposure-cross-ap.test.ts`) antes de inventar un mock nuevo.
6. Correr typecheck, lint y tests, y corregir lo que rompa.

## Fuera de alcance

- Dejar que el AP EDITE el `relationship`/`referrer` de una Person que ya existe — solo puede
  elegirlo en el momento de crear una Person nueva desde `preApprove`. Editar una Person ya
  vinculada sigue siendo exclusivo del dashboard de Augusto (`app/dashboard/persons`). Si más
  adelante se decide que el AP también deba poder editar vínculos existentes, es un feature aparte
  (implica una decisión de confianza distinta: dejar que el AP cambie un dato ya fijado, no solo
  declarar uno nuevo).
- Tocar `resolvePerson` (`server/services/identity.service.ts`) o cualquiera de sus otros callers —
  esa función no crea Persons, no necesita cambios para este feature.
- Cambiar la lógica de `checkRelationshipLimit` o los límites por tier (`DEFAULT_RELATIONSHIP_LIMITS`)
  — este feature solo cambia qué dato queda guardado, no cómo se evalúa.
- Agregar 'desconocido' como opción elegible en el selector — no es una opción real del enum en la
  UI existente del dashboard, se mantiene la misma paridad (3 opciones).
- El flujo de `approvePreApproval` (desembolso) o cualquier otra creación de Person fuera de
  `preApprove`.

## Restricciones clave

- **Nunca sobreescribir el `relationship`/`referrer` de una Person que ya existía antes de este
  `preApprove`** — es la regla de seguridad central de este feature. Solo se escribe en el momento
  de creación (`matchedBy === 'created'` en `resolvePersonByIdentity`).
- La TNA/tasa nunca debe mostrarse en vistas de prestatario — no aplica directamente a estos campos
  nuevos, pero es una restricción absoluta del proyecto a no romper en el copy que se agregue.
- Sin librerías nuevas — `Select`/`SelectTrigger`/`SelectContent`/`SelectItem` ya están disponibles
  en `app/ap/page.tsx`.
- No hacer estos campos obligatorios para pre-aprobar — deben poder omitirse sin fricción, igual que
  hoy.
