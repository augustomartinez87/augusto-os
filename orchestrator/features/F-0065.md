## Contexto

= S-048 del backlog. Incidente real 2026-08-31 corriendo F-0042: Claude Code devolvió el límite de sesión (`"You've hit your session limit · resets 4:40pm"`) con todos los contadores de tokens en 0. El loop lo trató como fallo de implementación: reintentó, escaló a Opus, y el fixer gastó sus 2 intentos contra un problema inexistente antes de bloquear el step (2 llamadas a Opus desperdiciadas + `STATE.json` a desbloquear a mano).

**Diagnóstico verificado contra el código (2026-09-29, Cowork):**

1. **Solo el builder detecta el límite.** `isUsageLimitError` / `handleUsageLimit` se usan únicamente en `executor.ts` (`executeStep` ~línea 199 y `executeStepWithRetry` ~línea 231). `escalation.ts` (`invokeFixer`) no tiene ninguna detección: un 429 sale con `exitCode !== 0` → `ok:false` → cuenta como intento fallido; con `MAX_FIXER_ATTEMPTS = 2` se gastan los 2 y se bloquea. `reviewer.ts` (`defaultCallClaude`) tampoco: con `exitCode !== 0` tira una excepción, y si el CLI devuelve exit 0 con el texto del límite en `result`, `parseReviewOutput` cae en el fail-safe `approved:false, feedback:text` (~línea 116) y el loop lo trata como CHANGES_REQUESTED, quemando reintentos y alimentando al builder con basura.
2. **El detector es frágil** (`limits.ts:17-25`). Busca `output.includes('rate limit')` / `'usage limit'` (case-sensitive) y `/\b429\b/` sobre TODO el output (stdout+stderr, `all:true`). Consecuencias: (a) falso positivo — un JSON de éxito con `"total_cost_usd":0.429…` o `"duration_ms":429`, o un builder que implementa un rate limiter y menciona "rate limit" en su `result`, dispara una pausa innecesaria; (b) falso negativo — "You've hit your session limit" no matchea ningún patrón de texto y solo se detecta si además viene `api_error_status:429` en el JSON.
3. **El parser de hora de reset no entiende el mensaje real.** `parseResetTime` (`limits.ts:33-48`) solo acepta `retry-after N` y `resets? at HH:MM` (24h, dos dígitos). "resets 4:40pm" no matchea → `hasExplicitResetTime` da false → sondeo ciego cada 15 min en vez de dormir hasta la hora real (que el propio mensaje informa).
4. **El "verifier" no es el culpable** (el backlog lo nombra así por el síntoma): `runVerifier` (`verifier.ts`) solo corre typecheck/lint/tests, sin LLM; los tests fallan porque el builder no escribió nada. Lo que hay que cortar es la cadena builder → reintentos → fixer, no el verifier.

**Lo que NO pude verificar:** el log del 429 original de F-0042 ya no existe (los logs por step, `logs/F-XXXX-stepN.log`, se sobrescriben en cada intento; los que quedaron son de la corrida exitosa, con `"api_error_status":null`). No se sabe si en ese incidente llegó `api_error_status:429`, solo el texto, o exit code distinto de 0. Por eso el detector nuevo debe cubrir las tres formas (ver pasos).

**Forma real de la salida de `claude -p --output-format json`** (verificada en `logs/F-0042-step1.log`): un objeto JSON con `type:"result"`, `is_error`, `subtype`, `api_error_status` (null en éxito), `result` (texto), `session_id`, `usage`, `total_cost_usd`, `duration_ms`. `parseClaudeJson` en `metrics.ts` ya lo parsea.

REUSAR:
- `parseClaudeJson` (`metrics.ts`) para extraer el JSON de resultado.
- El patrón de inyección para tests ya usado en `limits.ts` (`ProbeOpts`: `probeFn`, `sleepMs`, `sleepUntilFn`), en `escalation.ts` (`EscalationOpts.invokeFixerFn` / `runVerifierFn`) y en `reviewer.ts` (`callClaude?` injectable).
- `handleUsageLimit` tal cual (sleep hasta reset explícito + poll de `probeAvailability`); no reescribirlo.
- Suites existentes: `limits.test.ts`, `executor.test.ts`, `escalation.test.ts`, `reviewer.test.ts` como base para los tests nuevos.

## Pasos sugeridos (el planner puede refinar)

1. **`limits.ts` — detector estructurado.** Refactorizar `isUsageLimitError(output)` (mantener el nombre y la firma: lo usan `executor.ts` y `isProbeAvailable`): primero intentar extraer el objeto JSON de resultado del output (puede venir mezclado con stderr por `all:true`; extraer el primer objeto con `"type":"result"`, tolerante a basura antes/después). Si se parsea: es límite de uso solo si `is_error === true` Y (`api_error_status === 429` O `result` matchea, case-insensitive, `session limit|usage limit|rate limit|limit reached|too many requests|usage_limit_reached`). Si `is_error === false`, NUNCA es límite, sin importar qué diga el texto. Si NO se puede parsear JSON (stderr crudo, crash del CLI): fallback de texto case-insensitive con los mismos patrones más `"api_error_status"\s*:\s*429`, `HTTP 429` y `status(?: code)?[:\s]+429`; eliminar el `\b429\b` suelto. Tests unitarios con fixtures: éxito con `0.429` en costo, éxito con `duration_ms:429`, éxito con 'rate limit' en `result`, error con `api_error_status:429`, error solo con texto de session limit, stderr crudo con 'HTTP 429'.
2. **`limits.ts` — reset 12h.** Extender `parseResetTime` y `hasExplicitResetTime` para aceptar `resets? (at )?H:MM(am|pm)` y `Ham|pm` (sin minutos), case-insensitive, con espacio opcional antes de am/pm; mantener el formato 24h actual y `retry-after`. Convertir 12h→24h correctamente (12am=00:00, 12pm=12:00) y aplicar la regla existente (hora ya pasada → día siguiente). Tests: `resets 4:40pm`, `resets at 4:40 PM`, `resets 12am`, `resets 12:05pm`, cruce de medianoche, y que los formatos previos siguen funcionando.
3. **`escalation.ts` — el fixer respeta el límite.** Agregar `usageLimit?: boolean` a `FixerInvocationResult`; en `invokeFixer`, si `isUsageLimitError(output)` (o `exitCode === 429`), devolver `{ ok:false, usageLimit:true, ... }`. En `escalateStep`, si `invoked.usageLimit`: `await handleUsageLimit(invoked.output, state, opts?.usageLimitOpts)` y repetir el mismo intento (`attempt--`; `continue`) sin tocar `lastDetail` ni consumir presupuesto. Agregar `usageLimitOpts?: ProbeOpts` a `EscalationOpts` para testear sin dormir. Tests con `invokeFixerFn` inyectado: (a) limit → ok, el intento no se cuenta y devuelve `ok:true`; (b) limit → limit → ok; (c) fallo real → fallo real agota `MAX_FIXER_ATTEMPTS` como hoy (no regresión).
4. **`reviewer.ts` — el reviewer respeta el límite.** En `defaultCallClaude`, si la salida cruda es límite de uso (`isUsageLimitError` sobre `result.all`, o `exitCode === 429`), lanzar un error tipado exportado desde `limits.ts` (`class UsageLimitError extends Error { output: string }`) en vez del `Error` genérico; el chequeo va ANTES del `exitCode !== 0` y antes de `parseReviewOutput`. En `runReviewer`, capturar `UsageLimitError` → `await handleUsageLimit(err.output, state)` → repetir la revisión (loop). Tests con `callClaude` inyectado que lanza `UsageLimitError` la primera vez.
5. **Verificación cruzada del builder.** Confirmar que `executeStep` y `executeStepWithRetry` siguen comportándose igual con el detector nuevo (ya usan `isUsageLimitError` + `exitCode === 429`); agregar en `executor.test.ts` los casos de falso positivo (éxito con 'rate limit' en `result`, `0.429` en costo) para asegurar que NO pausan, y el caso session-limit-solo-texto para asegurar que SÍ pausan y no consumen `attempt`.
6. Typecheck y `npm test` completos.

## Restricciones clave

- Mantener el nombre y la firma de `isUsageLimitError(output: string): boolean`, `parseResetTime` y `handleUsageLimit`: `isProbeAvailable` (`limits.ts`) usa `isUsageLimitError` invertida y hay tests existentes que dependen de eso.
- Ante la duda, el detector prefiere NO pausar cuando `is_error === false`: un falso positivo duerme el loop horas con tokens disponibles (el bug que S-036/F-0028 vino a evitar).
- Los tests no pueden invocar el CLI real ni dormir de verdad: usar los mecanismos de inyección existentes (`ProbeOpts`, `invokeFixerFn`, `callClaude`).
- No tocar `state.ts`, `git.ts`, `index.ts` ni `autopilot.ts` salvo que el planner demuestre que hace falta (el objetivo es que el fix viva en `limits.ts`, `escalation.ts` y `reviewer.ts`).
