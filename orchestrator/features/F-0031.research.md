## Riesgos y restricciones técnicas para: Sistema — QA visual usa qaBaseUrl del target activo en vez de hardcodear localhost:3000 (S-037)

**Resumen:** El cambio es localizado y de bajo riesgo: reemplazar el literal `'http://localhost:3000'` en index.ts:447 por `getTargetConfig().qaBaseUrl ?? 'http://localhost:3000'`, manteniendo `process.env.QA_BASE_URL` como override. El principal riesgo técnico es que el target 'sistema' tiene `qaBaseUrl: ""` (string vacío), y el operador `??` no trata el string vacío como nullish, por lo que el fallback a localhost:3000 no se activaría — se necesita usar `||` en ese tramo o cambiar targets.json. `getTargetConfig()` ya está importado y sigue el mismo patrón usado en líneas 302 y 325. No hay tests unitarios que cubran este código, y el mock de `getTargetConfig` en planner.test.ts omite `qaBaseUrl`, lo que podría generar falsos positivos si se extiende la cobertura de tests hacia el flujo QA.

### Archivos clave
- `orchestrator/src/index.ts`
- `orchestrator/src/targets.ts`
- `orchestrator/src/qa.ts`
- `targets/targets.json`
- `orchestrator/features/F-0031.md`

### Patrones a seguir
- process.env.QA_BASE_URL ?? getTargetConfig().qaBaseUrl ?? 'http://localhost:3000'
- getTargetConfig() ya se usa en index.ts:302 y :325 con el mismo patrón de ?? encadenado
- getTargetConfig() ya está importado en index.ts:21 (import { setActiveTarget, getTargetConfig })

### Dependencias relevantes
- playwright (chromium) — ya existente en qa.ts
- targets.ts (getTargetConfig, Target interface) — ya importado

### Riesgos / Restricciones
- qaBaseUrl vacío en target 'sistema' (targets.json: `"qaBaseUrl": ""`) rompe el fallback: `"" ?? 'http://localhost:3000'` retorna `""` porque `??` solo captura null/undefined, no string vacío — el fallback nunca se aplicaría para 'sistema'
- getTargetConfig() lanza error si activeTarget no está seteado (targets.ts:77) — si el flujo ejecuta runQA antes de setActiveTarget() en index.ts, la línea modificada rompe con excepción; aunque el flujo actual setea el target antes de llegar al step loop, cualquier refactor futuro podría romper esta dependencia de orden
- No existen tests unitarios que cubran la línea de baseUrl en index.ts (index.test.ts no testea el loop QA) — el cambio queda sin cobertura de regresión
- El mock de getTargetConfig en planner.test.ts no incluye qaBaseUrl — si algún test nuevo del flujo QA mockea el mismo objeto sin esa propiedad, el acceso a .qaBaseUrl devolvería undefined y el fallback funcionaría, pero mock incompleto puede enmascarar errores
- El mensaje de error en qa.ts:72 menciona explícitamente 'QA_BASE_URL=<url>' como hint al usuario — si en el futuro se elimina el soporte de QA_BASE_URL como env var, ese mensaje quedaría desactualizado
