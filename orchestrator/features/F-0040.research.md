## Investigar qué existe para implementar: Kredy — plazo personalizado en el simulador del AP (hoy solo hay presets)

**Resumen:** El plazo en el simulador del AP (app/ap/page.tsx) hoy se elige solo entre presets config.terms (CSV default '3,6,9,12' en AgentConfig.terms, parseado en server/routers/ap.ts getConfig), pero la infraestructura ya acepta termMonths arbitrario: la mutación simulate recibe el int directamente y tanto el simulador público (server/routers/public-simulator.ts, zod 1..360) como el simulador interno de Kredy (app/dashboard/simulator/page.tsx addCompareTerm) son precedentes de plazos custom. El implementador debe tocar la UI de app/ap/page.tsx (agregar input libre junto a las pills), replicar la validación 1..360/máx 4, y considerar el impacto del ajuste por plazo DurationAdjustment (getTermAdjustment devuelve 0 fuera de rango) y del flujo de pre-aprobación/originación.

### Patrones a seguir
- config.terms.split(',').map(Number).filter(n => 0 < n) — los presets de plazo se guardan como CSV (default "3,6,9,12") en la DB y se parsean en el router para devolver terms al cliente
- selectedTermMonths + config.terms.map(t => <button>{t}m</button>) — el simulador del AP (app/ap/page.tsx) solo renderiza pills de presets y guarda un único plazo seleccionado, no un rango
- getTermAdjustment / getEffectiveTna — lógica de ajuste por rango de plazos (DurationAdjustment.minMonths/maxMonths) que se reusa para tasas presets y personalizadas
- simulateMut.mutateAsync({ token, capital, termMonths, grossTna }) — la simulación del AP ya acepta termMonths arbitrario (int), no está limitada a presets a nivel API
- preApprove.mutateAsync({ ..., termMonths: simulation.termMonths, grossTna ... }) — el plazo elegido fluye a la pre-aprobación/originación, por lo que un plazo custom tiene impacto downstream
- z.number().int().min(1).max(360) + array min 1 max 4 — validación existente en public-simulator que sirve de precedente para aceptar plazos custom
- addCompareTerm (term > 0 && term <= 360 && !compareTerms.includes(term) && length < 4) — patrón ya implementado en el simulador interno de Kredy para sumar plazos custom a la comparación

### Riesgos / Restricciones
- El plazo custom queda fuera de los rangos de DurationAdjustment: getTermAdjustment devuelve 0 y la TNA efectiva pierde el ajuste por plazo (el rango más específico es por minMonths/maxMonths)
- El estado del AP hoy es single-term (selectedTermMonths) con 4 botones presets y useEffect que fuerza el default a config.terms[0]; agregar plazo custom requiere UI nueva (input) + manejo de grid dinámico
- Los presets viven en DB como CSV (AgentConfig.terms / PublicSimulatorConfig.terms default '3,6,9,12'); el plazo custom no debería persistirse necesariamente, pero hay que decidir si queda solo en sesión/share o se agrega a la config
- Cualquier plazo fuera de 1..360 debe validarse con zod y el máximo permitido por producto; el share sheet y el mensaje de WhatsApp usan termMonths y deben soportar el valor custom
- La DB local apunta a PROD (ver SKILL.md): cualquier migración de schema requiere OK explícito de Augusto; idealmente implementar plazo custom sin tocar schema
- La comisión del AP y la originación asumen plazos del catálogo; validar impacto en PreApproval/Opportunity si se permite cualquier plazo [NO VERIFICADO]
