## Contexto

= S-042 del backlog. Decisión pendiente: "evaluar si vale la pena un `check-repo-health` (git status + tsc) que las sesiones manuales corran antes/después de trabajar, o si alcanza con la disciplina de no correr 2 sesiones de Claude Code en el mismo repo a la vez".

Decisión tomada (Cowork, 2026-07-24): construirlo. Motivo — durante F-0031 (esta misma sesión) se reprodujo en vivo el patrón exacto que motivó S-042: otra sesión escribió sobre `system/BACKLOG.md` mientras el loop corría, generando contención de working tree que bloqueó el merge automático (ver ADR-0091). La disciplina documentada ("no correr 2 sesiones en paralelo") no tiene ningún enforcement técnico y en la práctica hoy corren varias sesiones de Cowork simultáneas sobre distintos repos del monorepo. Un chequeo barato de 10 segundos reduce el tiempo de detección de este tipo de incidente.

Este script es **solo diagnóstico** — no bloquea ni serializa nada (eso sería un cambio de arquitectura mayor, fuera de alcance acá). Es el equivalente en código de los pasos 1 y 3 del diagnóstico manual documentado en `RUNBOOK.md §5`.

REUSAR: `getTargetConfig()`/`getRepoRoot()` de `targets.ts` (ya expone el path por target); patrón de CLI standalone de `intake-cli.ts` (recibe el target como arg); patrón de invocación de `execa` para `tsc --noEmit` ya usado en `verifier.ts:13-21,25-29` (mismo comando, mismo cwd — copiar el helper `run()`, no importarlo de `verifier.ts` para no acoplar el health-check al flujo del loop).

## Pasos sugeridos

1. Nuevo `orchestrator/src/check-repo-health.ts`: recibe `<target>` como argv, resuelve `getRepoRoot()`/`getTargetConfig()` (reusa `setActiveTarget` como hace `intake-cli.ts`).
2. Chequeo de working tree: `execa('git', ['status', '--porcelain'], { cwd })` — si hay output, listar archivos sucios.
3. Chequeo de lock huérfano: `existsSync(path.join(cwd, '.git', 'index.lock'))` — si existe, leer `statSync(...).mtime` y reportar antigüedad (sin matar procesos ni asumir nada — solo informar, la decisión de intervenir queda en RUNBOOK §5 manual).
4. Chequeo de typecheck: `execa('npx', ['tsc', '--noEmit'], { cwd })`, reportar OK/FAIL + output si falla.
5. Resumen final legible (✅/⚠️) + exit code acorde; script `"check-repo-health": "tsx --env-file=.env src/check-repo-health.ts"` en `orchestrator/package.json`.
6. Test unitario cubriendo al menos: detección de lock presente/ausente, parseo de `git status --porcelain` con y sin cambios (mockeando `execa`, mismo patrón de inyección que otros módulos).

## Fuera de alcance

- Cualquier forma de lock/enforcement que bloquee correr 2 sesiones en paralelo (sería resolver S-042 por prevención, no por diagnóstico — cambio de arquitectura mayor, no pedido).
- Listado de procesos vivos (`Get-CimInstance`/`tasklist`) — es específico de Windows y requiere shell interactivo; queda como paso manual documentado en RUNBOOK.
- Integrar el chequeo automáticamente dentro del loop (`index.ts`/`acquireRunLock`, ya cubierto por S-041) — este script es para sesiones MANUALES fuera del loop.
- Recuperación automática (borrar el lock, hacer `git checkout HEAD --`) — el script informa, no actúa.

## Restricciones clave

- Sin dependencias nuevas (usar `execa`, ya en `package.json`).
- No modificar `targets.ts`, `verifier.ts`, `git.ts` ni `index.ts` — es un script standalone nuevo.
- No debe requerir DB ni variables de entorno de ningún target — funciona igual para `dbModel: none` y `dbModel: prisma`.
