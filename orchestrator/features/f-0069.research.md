## Identificar riesgos y restricciones técnicas para el bug S-049: el Scout descarta el research completo cuando DeepSeek devuelve respuestas cortadas por max_tokens.

**Resumen:** El bug S-049 tiene una causa raíz clara y acotada en orchestrator/src/scout/deepseek.ts: el body del fetch a DeepSeek fija `max_tokens: 4096` hardcodeado y el loop solo maneja `finish_reason === 'tool_calls'`, sin branch para 'length'. Cuando la respuesta final se corta, el regex de extracción de JSON produce un payload inválido, `JSON.parse`/`ScoutReportSchema.safeParse` fallan y el agente lanza excepción; si las tres investigaciones corren la misma suerte, index.ts ve `reports.length === 0` y devuelve null, perdiendo todo el research (costo ya pagado). El fix debe respetar el contrato de report.ts (ScoutReportSchema/EvidenceItemSchema), la convención de `recordInvocation` dentro del finally y el fallback `research === null` declarado en SCOUT-KGL-DESIGN.md. No verifiqué el tramo final de index.ts ni scout.test.ts, que son los puntos con mayor probabilidad de tests rotos.

### Riesgos / Restricciones
- CAUSA RAÍZ: `max_tokens: 4096` está HARDCODEADO en el body del fetch a DeepSeek (deepseek.ts). No hay env/config que lo suba; un informe con evidencia detallada puede superar 4096 tokens de salida y cortarse.
- `finish_reason === 'length'` NO se maneja. El loop solo bifurca por `finish_reason === 'tool_calls'`; cualquier otro valor cae al branch 'Model finished' y trata la respuesta truncada como final.
- `JSON.parse(jsonMatch[0])` NO está envuelto en try/catch: un JSON truncado lanza SyntaxError que propaga y aborta el agente. Además el regex `\{[\s\S]*\}` es greedy y sobre un JSON cortado matchea desde la primera llave hasta el final (posiblemente), generando un parse inválido.
- Pérdida total, no parcial: en index.ts, si `reports.length === 0` (o si el corte deja solo JSON inválido) `runScout` devuelve `null` y se loguea 'continuando sin research'. No hay recuperación, reintento de continuación (continuation) ni cache del research parcial ya generado.
- Tras el fallo de una investigación, el agente lanza excepción; con `Promise.allSettled` solo se salvan las otras 2. Pero si las 3 se cortan (p.ej. mismo límite de tokens con respuestas largas), se pierde TODO el research aunque las búsquedas y tool calls ya se habían gastado (costo pagado, valor cero).
- Métrica y semántica de exit code: el `finally` llama `recordInvocation` con `exitCode = 1` en fallo, así que un corte por max_tokens se registra como error y el `costUsd` igual se cobra. Un fix que agregue reintentos/continuation cambia el significado de tokens y costo por feature — hay que revisar metrics.ts y sus tests.
- Restricción de contrato de salida: report.ts ya acepta strings libres (`archivos: string[]`), pero el JSON final del modelo se extrae con un regex de la prosa; cualquier cambio que toque cómo se parsea la respuesta final debe mantener compatible `ScoutReportSchema.safeParse` y `validateEvidence`.
- Riesgo de romper el fallback declarado: el diseño exige que `research === null` deje los prompts intactos. Una solución que introduzca 'research parcial' debe respetar el tipo `ScoutReport`' y `ScoutResult` para no romper architect.ts / planner.ts / executor.ts que consumen `research`.
- [NO VERIFICADO] No pude leer el tramo final de index.ts (escritura de `features/F-XXXX.research.md`/`.json`) ni scout.test.ts, así que no confirmé qué asserts existentes dependen del `max_tokens: 4096`, del branch de `finish_reason` o del throw por JSON inválido — son los tests con mayor probabilidad de romperse al cambiar el loop.
- [NO VERIFICADO] No confirmé la firma exacta de `recordInvocation` en metrics.ts ni si hay un test que valide `exitCode`/`costUsd` del scout.
