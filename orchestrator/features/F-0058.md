## Contexto

**Esta es una revisión de un intento anterior de F-0058 que se abortó a mitad de camino** al descubrirse, durante la implementación (no en este spec original), un problema real de diseño: la columna 39 del bulk `pb_get` (`cafci_fondo_padre`, "Id Fondo CAFCI padre") — que el spec original asumía disponible para construir la URL de detalle de cada clase — **solo viene poblada en ~9 de ~3.974 filas activas** (confirmado por el propio script al inspeccionar el archivo real). Para el 99,8% restante no hay forma de armar `/fondos/{padre}?clase={cafci_id}` con el dato del bulk.

**Se evaluó y se descartó un atajo** (usar `cafci_id` directo como si fuera el padre cuando no hay dato: `/fondos/{cafci_id}`) **verificándolo en vivo contra 3 fondos reales elegidos al azar** de `fci_master`: 2 de 3 dieron error 404, y el tercero (`cafci_id=1819`, "Balanz Institucional - Clase B") cargó la ficha de un fondo completamente distinto ("Delta Ahorro Dólares") porque ese número coincidió por casualidad con el ID de OTRO fondo padre. Ese atajo escribiría datos de comisiones de un fondo en el registro de otro — peor que un fallo, es corrupción silenciosa de datos. Descartado.

**Investigación que sí dio un camino viable** (verificado en vivo contra estadisticas.cafci.org.ar):
- No existe una URL que resuelva por clase sin el padre: `/fondos?clase={id}` y `/clases/{id}` devuelven 404 ambas.
- `/fondos/{id}` (SIN `?clase=`) sí carga usando solo el ID del fondo padre, mostrando una clase representativa del fondo (ej. ID `1` → "Blacktoro Ahorro - Clase B"; no siempre es la Clase A). Esto permite obtener el nombre base del fondo y su gerente sin necesitar saber de antemano ningún `cafci_id` de clase.
- El espacio de IDs de fondo padre es mucho más chico que el de clases y con huecos (fondos dados de baja): probado en vivo, IDs `1`, `798`, `1625`, `1804`, `1850` cargan una ficha válida; `1900`, `2000`, `2200`, `2500`, `2800`, `5000`, `9000` dan 404. El máximo válido encontrado en esta muestra fue `1850` — se recomienda crawlear con margen (ver Pasos) y tratar cualquier ID fuera de rango simplemente como "no existe" (404), sin que eso rompa nada.
- Esto habilita una Fase 0: crawlear ese rango acotado UNA VEZ (o incrementalmente), sacar nombre+gerente de cada fondo padre válido, y cruzarlo por nombre (sin sufijo de clase) + gerente contra las clases del bulk para armar el mapa `cafci_id → cafci_fondo_padre` nosotros mismos, sin depender del dato ausente del bulk.

**Por qué guardar `cafci_fondo_padre` en `fci_master` en vez de resolverlo en memoria cada vez:** persistirlo permite que la Fase 0 sea mayormente un costo de UNA SOLA VEZ — las corridas mensuales siguientes solo necesitan crawlear para clases nuevas (fondos lanzados después de la última corrida) o las que quedaron sin match, no repetir el barrido completo de ~2.000 IDs cada mes.

**Presupuesto de tiempo:** la primera corrida cubre Fase 0 (~2.000-2.500 requests, rango a crawlear) + Fase 1 (~3.974 requests, scraping de detalle) ≈ 6.000 requests con rate limiting — puede tomar 60-100 minutos. Corridas mensuales posteriores son mucho más rápidas (Fase 0 casi vacía, solo clases pendientes). El job de GitHub Actions necesita `timeout-minutes` generoso pensado para la primera corrida.

## Pasos sugeridos (el planner puede refinar)

1. Migración aditiva en `fci_master`: `cafci_fondo_padre integer null` (para el mapeo) + las columnas de liquidez/comisiones ya definidas en el acceptance (`plazo_liquidacion_dias`, honorarios, comisiones, `liquidez_updated_at`).
2. Script `scripts/cafci_liquidez_sync.py` — módulo de Fase 0 (resolución de fondo padre):
   - Función que, dado un rango de IDs (parametrizable; default sugerido `range(1, 2500)` con margen sobre el máximo válido observado de 1850), hace `GET /fondos/{id}` para cada uno con el mismo rate limiting que la Fase 1 (ver Restricciones), tolera 404 (skip silencioso, no es un error), y de cada página válida extrae el nombre base del fondo (quitando el sufijo "- Clase X") y la sociedad gerente.
   - Solo ejecutar este crawl para clases de `fci_master` con `activo = true` Y `cafci_fondo_padre IS NULL` — si no quedan clases pendientes, saltear la Fase 0 por completo en esa corrida (log explícito de "Fase 0 saltada: todas las clases ya tienen fondo padre resuelto").
   - Matchear cada fondo padre encontrado contra las clases pendientes por nombre base + gerente/sociedad_gerente (nunca solo por nombre — nombres de fondo pueden repetirse entre gestoras distintas, y ya vimos el costo de un match falso). Persistir los matches exitosos vía upsert por lotes a `fci_master` (`on_conflict="id"`, solo `{id, cafci_fondo_padre}`).
   - Loguear cuántas clases quedaron sin resolver al final de la Fase 0 (sin abortar; simplemente esas clases no se scrapean en la Fase 1 hasta que se resuelvan).
3. Fase 1 (scraping de detalle), igual al diseño original: para cada clase activa con `cafci_fondo_padre` resuelto (ya sea desde esta corrida o de una anterior), armar `/fondos/{padre}?clase={cafci_id}`, hacer `GET`, parsear con un parser tolerante los campos de liquidez/comisiones (campo puntual no encontrado o no parseable → loguear y dejar `null` solo ESE campo, nunca descartar la clase entera — cuidado particular con `comision_exito_pct`: distinguir "guión → null válido" de "valor presente pero no parseable → omitir el campo, no guardar null").
4. Rate limiting en AMBAS fases: delay fijo entre requests (recomendado 300-500ms) + timeout razonable por request (ej. 15s) + reintentos acotados (2-3) antes de saltear y loguear como fallido.
5. Flags `--limit N` y `--dry-run`, aplicables independientemente a Fase 0 y Fase 1 (por ejemplo `--fase 0 --limit 50 --dry-run` para validar solo el matching de nombre+gerente contra una muestra chica del rango de fondos, y `--fase 1 --limit 30 --dry-run` para validar el parser de detalle contra clases ya resueltas). Correr ambas muestras y confirmar manualmente antes de habilitar el cron completo.
6. Upsert por lotes a `fci_master` en ambas fases, solo con los campos parseados/resueltos con éxito en esa corrida — nunca pisar un valor bueno anterior con `null` por un fallo puntual.
7. Workflow nuevo `.github/workflows/cafci_liquidez_monthly.yml`: cron mensual (ej. día 1 a las 03:00 UTC) + `workflow_dispatch`, `timeout-minutes` generoso (ej. 180, pensado para la primera corrida con Fase 0 completa), mismos secrets (`SUPABASE_URL`/`SUPABASE_SERVICE_KEY`) que `cafci_daily.yml`.
8. Tests: mockear los requests HTTP. Cubrir Fase 0 (matching por nombre+gerente: caso match exacto, caso sin match, caso de nombres iguales entre gestoras distintas que NO deben matchear entre sí) y Fase 1 (parser: los 3 casos reales ya verificados — plazo 0 y 1 día, honorarios separados gerente/depositaria, comisión de éxito ausente → null). Typecheck del repo.

## Fuera de alcance

- Mostrar estos datos en el Explorador (columna, filtro, tooltip) — este feature es solo persistencia. Surfacing en UI queda para una iteración futura.
- Historizar estos campos en el tiempo — solo el valor actual por clase.
- Resolver casos de fondos con estructura de página distinta a las verificadas (fondos cerrados, instrumentos atípicos) más allá de loguearlos como fallidos.
- Ampliar el rango de crawling de Fase 0 "por las dudas" mucho más allá del margen razonable sobre el máximo válido observado (1850) — si tras la primera corrida quedan clases sin match y el log lo confirma, ampliar el rango es una iteración futura puntual, no algo para sobredimensionar de entrada.
- Resolver manualmente (a mano, por Augusto) los casos raros que ni por nombre+gerente logren match — quedan como pendientes logueados, no bloquean el resto.

## Restricciones clave

- El matching de Fase 0 usa SIEMPRE nombre base + gerente/sociedad_gerente juntos — nunca solo nombre. Ya se comprobó el costo de un match incorrecto (fondo A pisando datos de fondo B).
- Nunca abortar la corrida completa por el fallo de un fondo/clase individual (ni en Fase 0 ni en Fase 1).
- Nunca pisar un valor bueno anterior (`cafci_fondo_padre` incluido) con `null` por un fallo puntual de esa corrida — dejar el valor viejo tal cual.
- Delay obligatorio entre requests en AMBAS fases — nunca ráfagas sin pausa.
- Correr `--limit` + `--dry-run` de Fase 0 Y de Fase 1 por separado contra muestras reales, y confirmar el resultado manualmente, ANTES de habilitar el cron mensual completo.
- Migración estrictamente aditiva.
- La Fase 0 se salta por completo (no se re-crawlea el rango) cuando ya no quedan clases activas con `cafci_fondo_padre IS NULL` — esto es lo que mantiene rápidas las corridas mensuales después de la primera.
