## Riesgos y restricciones técnicas para: Sistema — check-repo-health, diagnóstico rápido para sesiones manuales fuera del loop (S-042)

**Resumen:** El check-repo-health (F-0032/S-042) es un script CLI standalone que debe reusar setActiveTarget/getRepoRoot de targets.ts y copiar el helper run() de verifier.ts sin importarlo, usando execa para git status --porcelain y tsc --noEmit. El riesgo principal es el estado global mutable de setActiveTarget (no thread-safe), paths absolutos Windows en targets.json que pueden no funcionar cross-platform, y la necesidad de mockear execa en tests sin precedente directo en el repo (los tests existentes usan inyección de funciones en lugar de vi.mock('execa')). Las restricciones clave incluyen no agregar dependencias nuevas, no modificar targets.ts/verifier.ts/git.ts/index.ts, y no requerir DB ni variables de entorno de ningún target.

### Riesgos / Restricciones
- setActiveTarget() usa estado global mutable (targets.ts:28 'activeTarget') — no es thread-safe; para el uso standalone planeado (sesiones manuales fuera del loop) es aceptable, pero si alguien lo corre mientras el loop principal está activo en el mismo proceso podría corromper el estado del loop.
- Los paths en targets.json son rutas absolutas Windows (C:/Users/Augusto/...) — el script puede fallar en otro OS o si el monorepo no está montado exactamente en esa ruta. getRepoRoot() devuelve el path tal cual está en targets.json.
- No debe depender de DB ni variables de entorno de ningún target (por el target 'argos' con dbModel:none y 'sistema' también dbModel:none) — la copia del helper run() de verifier.ts debe omitir getDbEnvOverride() porque el health-check no ejecuta contra la DB.
- La feature spec dice explícitamente 'copiar el helper run(), no importarlo de verifier.ts para no acoplar el health-check al flujo del loop' — ignorar esta restricción acoplaría el script a verifier.ts y a sus dependencias (db-guard).
- Los tests existentes usan inyección de dependencias (vi.mock + funciones injectables) en lugar de mockear execa directamente — no hay precedente en el repo de vi.mock('execa') [NO VERIFICADO: no encontré ningún test que mockee execa directamente, solo inyección de funciones como callClaude/probeFn].
- El script debe registrar un nuevo comando en package.json scripts: 'check-repo-health': 'tsx --env-file=.env src/check-repo-health.ts' — si no se agrega, npm run check-repo-health fallará.
- El target 'sistema' tiene scoutRoot diferente de path — el health-check usa getRepoRoot() (que retorna path), no getScoutRoot(), lo cual es correcto porque tsc debe correr en el directorio del orchestrator. Pero hay que asegurarse de que el chequeo de git status --porcelain también use ese mismo cwd.
- La detección de .git/index.lock requiere que el directorio tenga un subdirectorio .git/ — si el path del target no es un repo git válido, existsSync devuelve false silenciosamente; el script debería considerar este caso como advertencia.
